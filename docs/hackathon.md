## 5. Show that the invention really works

Technical execution is worth 20%, but a credible evaluation also strengthens the impact and demo scores.

I would prepare a compact test dataset of around 12–20 scenarios, including contradictory claims, genuinely compliant systems, incomplete evidence and an adversarial document containing an attempted prompt injection.

Compare two systems:

| Baseline | Show Me |
|---|---|
| Muse Spark summarises interviews and documents | Muse Spark/Wonder investigates with tools and executes tests |
| Produces risk assessments | Produces evidence-linked, testable findings |
| Relies on what people say | Can check selected claims against observed behaviour |

Measure **true contradictions detected, false accusations, successful test execution, unsupported claims, and investigation time**. Run multiple trials and show actual results, including failures.

Then ask your privacy officer co-founder to review blind cases and explain whether the results would be useful in their day-to-day work. One authentic practitioner's assessment is better evidence of commercial demand than invented revenue projections.

For the Startup track, this matters enormously. Judges are expressly looking for something that can function as a real product. <Cite ref="turn343494view1"/>

### What I'd cut

Don't build the whole Dunstan.AI platform. Don't implement enterprise SSO, broad compliance frameworks, a giant RAG pipeline, autonomous phone calling infrastructure, or Kubernetes orchestration just for this entry.

**Yes, as an experimental visual-reconstruction workflow. But it works better on individual objects than on an entire aerial landscape.**

| Feature | What I'd use |
|---|---|

| Driveway and paths | SAM 3.1 masks → surface geometry |

### How masks improve SAM 3D reconstruction

For example, SAM 3.1 might identify a shed and return a mask showing precisely which pixels belong to it.

We give SAM 3D both the original image and the shed's mask. SAM 3D can then focus its reconstruction on that object while retaining context from the photograph.

This should help with object isolation and reduce irrelevant background content. It does **not** add missing depth information or guarantee a more accurate shape.

The official repository supports this exact image-plus-mask interface. It also supports exporting GLB files and Gaussian splats. <Cite refs={["turn882309search0","turn385767view2"]}/>

### Example integration

Once SAM 3.1 has generated a mask, the following illustrates how to call the official SAM 3D inference pipeline:

<CodeBlock language="python" editable>
import sys
import numpy as np
from PIL import Image

sys.path.append("notebook")
from inference import Inference, load_image

# Image and mask must share pixel dimensions.
image = load_image("property-aerial.png")
mask = np.asarray(
    Image.open("shed-mask.png").convert("L")
)

pipeline = Inference(
    "checkpoints/hf/pipeline.yaml",
    compile=False,
)

result = pipeline(image, mask, seed=42)

# Export a mesh for Blender where available.
if result.get("glb") is not None:
    result["glb"].export("shed.glb")

# Alternatively retain the Gaussian-splat output.
result["gs"].save_ply("shed-splat.ply")
</CodeBlock>

This assumes SAM 3D's environment and model checkpoints have already been installed, and that the SAM mask has been decoded into an image-aligned grayscale mask.

One useful distinction: the GLB is an editable 3D asset, although it won't necessarily have clean architectural topology. The Gaussian splat is primarily useful for visual rendering rather than geometry validation.

## 6. Running SAM 3D on our GPU infrastructure

SAM 3D Objects is distributed as model weights and inference code. It isn't listed as the same hosted `sam-3.1` endpoint.

Meta's official setup specifies Linux x86-64, an NVIDIA GPU with at least **32 GB VRAM**, and separately requested Hugging Face checkpoint access. <Cite ref="turn285010view1"/>

For our pipeline:

| Service | Suggested execution |
|---|---|
| SAM 3.1 object segmentation | Meta Model API |
| SAM 3D Objects reconstruction | Modal L40S 48 GB, or local 32 GB+ NVIDIA GPU |
| GIS processing | Python CPU worker |
| Blender scene generation | CPU worker, with GPU rendering where needed |
| Final Cycles render | Modal GPU worker |

I'd separate the SAM 3D process from Blender, since their CUDA and Python dependencies may differ and they don't need to occupy GPU memory simultaneously.

An L40S is a reasonable starting point, but we'll want to run the official example and measure actual VRAM and latency before depending on it.

# LiDAR + Meta AI: Teaching Muse to understand the physical world

**Yes. And I think this could become the most technically distinctive part of Button NZ's hackathon entry.**

Instead of merely providing Muse with an aerial photograph, we can give it several different *visual interpretations of the same physical property*—terrain elevation, surface heights, contours, slopes, 3D perspectives and segmented objects—and see whether it can develop a more accurate understanding of the scene.

The interesting research question is:

> Can a general-purpose multimodal AI model reason about a real 3D environment more effectively when we translate geometric data into different visual representations it already understands?

We wouldn't be training Muse. We'd be experimenting with **geospatial representation, multimodal reasoning and active perception**, then connecting those capabilities to Blender.

## 1. The big opportunity: LINZ gives us two different types of elevation

LINZ publishes both nationwide 1 m LiDAR-derived DEM and DSM products, with coverage determined by the underlying surveys. They're available as raster datasets, along with hillshades and, separately, survey point clouds. <Cite refs={["turn179221search0","turn179221search1","turn179221search2"]}/>

<grid columns={2} gap={3}>
  <grid-item>
    <AsyncImage query="digital terrain model bare earth lidar hillshade landscape no buildings vegetation side by side example" aspectRatio="5:4"/>
    **DEM — bare-earth elevation**

    <text size="sm" color="secondary">Represents the terrain with buildings and vegetation filtered out. Useful for slopes, ground levels, drainage investigation and terrain meshes.</text>
  </grid-item>
  <grid-item>
    <AsyncImage query="digital surface model DSM lidar building rooftops trees elevation rainbow map aerial high resolution" aspectRatio="5:4"/>
    **DSM — surface elevation**

    <text size="sm" color="secondary">Includes the upper surfaces of roofs, trees and other objects. Useful for understanding the above-ground environment.</text>
  </grid-item>
</grid>

The particularly interesting operation is:

\[
H_{\text{objects}}(x,y) =
DSM(x,y)-DEM(x,y)
\]

This produces an approximate *normalised surface-height model* (nDSM).

For example, an illustrative set of values might look like:

| Location | DEM | DSM | Difference |
|---|---:|---:|---:|
| Lawn | 100.2 m | 100.3 m | 0.1 m |
| House roof | 100.4 m | 105.8 m | 5.4 m |
| Large tree | 100.1 m | 109.3 m | 9.2 m |
| Shed roof | 100.3 m | 103.1 m | 2.8 m |

These numbers are illustrative, not actual LINZ measurements.

That gives us valuable geometric evidence before using a single AI model.

We can use GIS to construct the measured terrain, then ask Muse and SAM to infer what the elevated features are and how they relate to the rest of the property.

One caution: 1 m is the raster spacing, not a promise of 1 m positional accuracy. LINZ's national DSM advertises a vertical accuracy specification of ±0.2 m and horizontal accuracy of ±1.0 m at 95% confidence. Source dates and actual conditions still matter. <Cite ref="turn353168view0"/>

That's compelling because the model's own rendered output is being tested against independent physical observations.

The same mechanism could later evaluate proposed housing concepts for collision and geometric feasibility.

## 8. How do we prove we're surfacing a new capability?

This is where we can turn a compelling demo into something resembling a small scientific experiment.

I'd benchmark Muse on a handful of properties using identical questions with different information representations.

| Experiment | Model receives | What we measure |
|---|---|---|
| Baseline | Aerial photo alone | Correct spatial interpretations |
| Contours | Aerial + contour drawing | Improvement on slope and relative-height questions |
| Height-aware vision | Aerial + DEM/DSM/nDSM views | Improvement on object heights and ground-versus-structure distinctions |
| Multiple perspectives | Aerial + synthetic 3D views/video | Improvement on relative positioning |
| Active perception | Muse chooses its own LiDAR visualisations and numerical queries | Correctness, tool usage and investigation cost |

Use known geometry and independently calculated answers as ground truth. Don't let a model grade itself.

For the hackathon, a compact benchmark of perhaps 5–10 diverse sites and 10–20 spatial questions per site would be enough to expose interesting behaviour. This won't establish general scientific superiority, but it can demonstrate a real, reproducible difference.

There is already academic interest in this precise gap: **Geo3DVQA**, published at WACV 2026, benchmarks vision-language models on height-aware 3D geospatial reasoning from aerial imagery. That gives us a relevant research framing. <Cite ref="turn699998search11"/>

The interesting outcome wouldn't necessarily be "Muse can read LiDAR."

It might be something like:

> "When Muse was given ordinary aerial imagery, it struggled to infer terrain slope. After the agent generated and examined its own LiDAR cross-sections, it identified the correct building-pad orientation much more consistently."

We would only say that if the results actually support it.

## The demonstration I'd aim for

The strongest sequence would be:

**First**, Muse sees an ordinary aerial image and identifies where a prefab dwelling might go.

I'd measure:

- **Scene understanding:** correct object classification, object location and uncertainty recognition.
- **Geometric fidelity:** building footprint intersection-over-union and height error against independently established reference data.
- **Blender execution:** proportion of scripts or planned edits that execute successfully.
- **Design validity:** proportion of proposed layouts passing implemented deterministic checks.
- **Efficiency:** model latency, inference cost, and number of corrections needed.

For a small hackathon dataset, report the number of independent sites and show individual successes and failures—not just a single accuracy percentage.

Avoid letting synthetic examples from one site leak into training and validation through different camera angles or colour palettes. Split by property or generated-scene family.

## 8. The alternative: fine-tune a much smaller satellite vision model

If the main objective is recognising roofs, vegetation, driveways and garden features, rather than teaching an LLM to reason about them, we have another strong option.

Meta's <Entity category="software" value="DINOv3-SAT" disambig="Meta satellite-trained visual foundation model"/> has a **300-million-parameter ViT-L variant** trained on 493 million satellite images.

We could freeze the model and train a lightweight segmentation head on human-corrected SAM 3.1 masks, potentially with additional height features from the nDSM. Meta's research explicitly demonstrates that DINOv3 features work well with lightweight task-specific adapters. <Cite refs={["turn129602search5","turn129602search6"]}/>

This is a much smaller training problem than fine-tuning a 30B model. It might yield more reliable object classification with limited labelled data, particularly for top-down imagery.

I'd keep it as an alternative if Glimmer multimodal training proves too expensive or yields limited improvements.

## 10. The capability I'd showcase to Meta

The most interesting demonstration isn't simply that we fine-tuned a model.

It's a **system that learns from its own validated design failures, using human corrections to improve its next version overnight**.

For example:

1. Muse interprets LiDAR views and proposes a building location.
2. Blender generates the scene.
3. A geometric evaluator discovers a placement problem.
4. A human approves a corrected scene plan.
5. That validated correction becomes a new supervised training example.
6. The next model release is evaluated on separate, unseen sites to determine whether the same type of mistake occurs less often.

That's an automated supervised-learning feedback loop—not RL.

It would give us two impressive things to show: an agent controlling real engineering software, and a measured improvement in its site-understanding or design decisions through task-specific training.

**My recommendation:** Start with Muse Glimmer multimodal QLoRA, 500–1,500 programmatically generated examples, and a small but carefully reviewed real-world dataset. Keep Muse Wonder/Spark responsible for executing Blender Python. Spend no more than a couple of days getting the first training pipeline working; if it fails to improve held-out results, divert that effort back into better LiDAR representations and tool-based feedback.

The combination most likely to impress the Meta judges is **not a big fine-tune, but a small, reproducible experiment demonstrating that their model gains a useful new spatial-design capability from the unusual data we're feeding it.**
